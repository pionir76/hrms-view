# HRMS

현대 남양 연구소 냉동기 모니터링 시스템 (Hyundai Namyang Refrigerator Monitoring System)

## 개요

현대 남양 연구소 내 냉동 관련 장비와 압축기의 운전 상태 및 센서 정보를 중앙 서버에서 통합 수집하고, 웹 기반 모니터링 시스템을 통해 확인할 수 있도록 하는 시스템입니다.

### 현재 목적

**2026년 8월 31일부터 정식 개발로 전환**했습니다. 초기에는 백엔드 API 기능 테스트 목적의 간단한 화면으로 시작했지만, 이제부터는 실제 사용자가 쓸 화면 기준으로 **디자인과 구성(레이아웃, 인터랙션, 가독성)에도 신경써서** 작성합니다. 다만 여전히 소규모(약 20명) 내부 시스템이므로 과도하게 화려한 디자인보다는 실용성과 일관성을 우선한다.

### 참고 사항

- 백엔드 기능 명세 및 업데이트 사항은 항상 [`reference/`](reference/) 폴더를 확인합니다 ([api-manual.md](reference/api-manual.md)). `reference/`는 백엔드가 통째로 갱신해 주는 자료라 git에서 관리하지 않는다.
- **배포**: 빌드 과정이 없다. 이 폴더에서 `.make-deploy.ps1`(PowerShell)을 실행하면 상위 폴더의 `deploy`에 화면에 필요한 파일(`index.html`, `pages/`, `common/`, `assets/`)만 담긴 전달용 폴더가 만들어진다(`mokup/`·`README.md`·`TODO.md`·`reference/`는 빠짐 — 서버에 올리면 누구나 열람 가능해서). 그 내용을 서버의 wwwroot에 덮어쓴다. 백엔드가 화면과 API를 같은 주소로 서비스하고, API 주소는 `common/js/config.js`가 **화면을 연 주소를 보고 자동으로** 고른다 — 개발 PC(로컬 파일·localhost·127.0.0.1, Live Server 포함)면 `http://localhost:80`, 그 밖(테스트 서버 `http://59.16.212.237/`, 납품 현장 폐쇄망)이면 상대 경로(`/api/...`)라 **IP가 바뀌어도 고칠 것이 없다**. 글꼴(Pretendard)은 폐쇄망 대비 `assets/fonts/`에 넣어 인터넷 없이 동작한다(2026-10-02).
- 이 문서와 `reference/` 문서의 내용이 서로 어긋나는 부분이 있으면, 화면 구현 전에 먼저 맞춰봐야 합니다 (하단 [11. 확인이 필요한 부분](#11-확인이-필요한-부분) 참고).

### 상단 (항상 고정)

    - **내 정보 = 읽기 전용 모달**: 성명·담당업무·ID 카드, 소속팀·직위·대직자·법정교육일·차기교육일·선해임 신고서(있으면 파일명을 눌러 받기), 담당장비(지역 → 시설동으로 묶어 나열, 건수 표시). 수정 기능은 없다.

    - **설정 = 설정 모달**(본인이 바꿀 수 있는 것만): 본인 연락처1·2 변경(69번)과 비밀번호 변경(68번). 비밀번호는 처음엔 "비밀번호 변경" 버튼만 보이고, 누르면 **① 현재 비밀번호 → ② 새 비밀번호(2번 입력) → ③ 완료 메시지** 순서로 진행한다. 현재 비밀번호만 확인하는 API가 없어(로그인 API로 확인하면 로그인 이력이 남는다) 실제 확인은 마지막 변경 요청에서 서버가 하고, 틀렸으면 ①단계로 되돌려 오류를 보여준다. 연락처·비밀번호는 API가 달라 따로 저장한다. 성명·소속팀·담당업무 등은 시스템관리자가 조직 관리에서 수정한다.
    - **로그아웃**은 확인 모달("로그아웃하시겠습니까?")을 거친다.
- 상단바 높이 64px, 스크롤해도 위에 붙어 있다. **1366px 폭까지 한 줄**에 들어가도록 좁아지면 아바타·소속팀(1560px 이하) → "남양연구소" 줄·날짜(1300px 이하) 순으로 숨긴다.
- 로고 원본(`assets/logo_master.png`)은 투명 배경의 흰색이라 CSS mask로 네이비(`--color-brand-navy: #002c5f`)를 입혀 쓴다.

## 3. 실시간 현황

2026-09-17 전면 개편(시안 v4 기준 — 시안 파일은 2026-09-18 정리 때 삭제, 화면 자체가 기준이다). 화면 한 장에 고정하고(페이지 스크롤 없음) **좌측(요약 카드 + 장비 리스트) : 우측 380px(시스템 정보 + 서버 상태)**, 맨 아래에 이벤트 티커를 둔다. 운영 상태 장비만 보여준다(70번 API가 운영 장비만 내려줌).

- **머리 줄**: 갱신 배지("실시간 · N초 전 갱신", 조회 실패 시 빨간 "연결 확인 필요"), 보기 전환 **리스트 / 맵**.
- **맵 모드**(2026-10-01, `dashboard-map.js`, 시안 `mokup/dashboard_map_v1`·`v2`): 요약 카드·장비 리스트 자리를 지도 카드가 차지한다. 지도는 `assets/main_map_f.svg`(사용자가 Inkscape로 관리, 같은 이름으로 덮어씀 — 화면이 매번 새로 받는다). `Area_A/B/C` 레이어의 도형 `<title>`을 DB `buildingName`과 **같은 지구 안에서 띄어쓰기·하이픈을 빼고** 비교해 연결하고(DB 이름 기준으로 지도 이름 정리 완료), 시설동을 소속 장비 중 가장 나쁜 상태로 칠한다 — 경보·비상정지(빨강, 깜빡임 + 붉은 빛) > 통신오류(주황, 점선 테두리 흐름) > 운전(초록, 숨쉬기 빛) > 정지(회색, 움직임 없음), 장비 없는 건물은 연회색. 배경은 파스텔 색이 천천히 흐르고, 캠퍼스 경계(`Map_Boundary`)는 흰 면, 녹지는 민트, 바탕 레이어의 채움 없는 닫힌 도형(트랙·도로)은 연한 회청색. 이름(title)이 있는 도형은 작고 옅게 **건물번호(Inkscape 라벨, 예: A1-5) / 시설동 이름** 두 줄로 표시(장비 있는 시설동만 조금 진하게). 좌측 상단에 방위(위쪽 북, N). 지도 바탕은 눈부시지 않게 차분한 회청색 계열. 지구 탭(전체/A/B/C), 확대·축소·맞춤(휠·드래그). **시설동 툴팁·팝업**(시안 `mokup/dashboard_map_hover_v1`): 마우스를 올리면 커서를 따라다니는 툴팁(건물번호 + 시설동명 + 장비 수, 누를 수 없음), **클릭하면 장비 목록 팝업**(닫기·Esc·빈 곳 클릭으로 닫힘). 처음엔 호버로 팝업을 띄웠으나 시설동이 가까우면 팝업으로 옮기는 도중 다른 건물로 바뀌어 클릭 방식으로 바꿈(사용자 2026-10-01). 머리 건물번호 + 시설동명, 상태별 대수, 장비 목록(나쁜 상태 순 — 상태 점·이름·압축기 수·상태 태그), 장비를 누르면 장비 실시간 화면으로 이동 — 이때 `from=map&tab=…`을 넘겨 그 화면의 "실시간 현황으로"가 맵 모드·보던 지구로 돌아온다. 실시간 현황 주소도 보기 상태를 반영한다(`?mode=map&tab=B`, 새로고침·뒤로 가기에도 유지). **운영 외 장비**(미운영·수리중 …)는 70번에 없어 1번 전체 목록에서 골라(맵을 열 때 + 5분마다) 팝업 맨 아래에 흐리게, 운영 상태 태그만 표시 — 시설동 색에는 넣지 않는다. 움직임 줄이기 설정이면 애니메이션 끔. 장비 상태는 리스트와 같은 70번 API(5초, 운영 장비만).
- **좌측 상단 — 요약 카드 3개**(장비 기준, 큰 아이콘 왼쪽 + 정보 오른쪽): **운영 장비**(옆에 미운영 장비 수를 약하게 — 8번 요약 API의 `equipmentCountByStatus`, 30초 갱신 / 아래 압축기 수·시설동 수). 이 화면의 숫자는 전부 운영 장비 기준이다 — 70·8번 API가 운영 장비만 집계하므로 "전체"가 아니라 "운영"이라고 쓴다(운영 149 + 미운영 9 = 등록 158), 운전 중인 장비(**운전 수 강조 / 전체 수 약하게**, 비율 막대), 통신 불량 장비(1대 이상이면 카드가 주황으로 강조).
- **좌측 하단 — 장비 리스트**: 필터 칩(전체/운전/정지/통신 불량/경보, 개수 표시) + 장비명·시설동 검색. A/B/C지구 3단, 지구마다 머리(대수·시설동 수·"운전 N · 통신 N · 경보 N")와 내부 스크롤, 시설동으로 묶음.
    - 행: 상태 점(운전 초록/정지 회색/통신 불량 주황) · 장비명 · **압축기 수량 배지**(회색 사각에 수량만, 색 변경 없음) · **통신/경보 on·off 배지**(항상 표시). 색은 **통신 = 주황, 경보 = 빨강**으로 상태 점·지구 머리·필터 칩·배지·요약 카드 모두 통일. 통신이 끊긴 장비는 경보 여부를 알 수 없으므로(위 3.1장 참고) 경보 배지를 점선으로 흐리게 표시한다.
    - 행 클릭 → [3.1 장비 실시간 화면](#31-장비-실시간-화면).
- **우측 패널(평소 접힘)**: 머리 줄 "시스템 상태" 버튼(서버·API 상태 중 나쁜 쪽을 점 색으로 표시)을 누르면 오른쪽에서 밀려 나오고 좌측이 그만큼 줄어든다. 열림 상태는 기억하지 않는다(새로 들어오면 접힌 상태).
- **우측 상단 — 시스템 정보**(30초 갱신, 71번): "저장소 사용량" 도넛(사용률) + 오른쪽에 사용량/전체 용량/남은 용량 세로 배치, CPU(코어 수)·메모리(사용/전체 GB) 막대 — 각각 왼쪽 아이콘.
- **우측 하단 — 서버 상태**: 서버 상태(정상/주의/오류), DB 백업(백업 기능이 없어 현재 "미설정"), 데이터 수집 주기(3초 · 수집 대상 압축기 수), API 상태(판정 + 프론트가 잰 응답 시간), 시스템 가동시간(**백엔드 서비스 시작 기준**, OS 부팅 아님). 측정 못 한 항목은 "-".
- **하단 — 이벤트 티커**: 장비의 경보·통신장애·비상정지 이벤트만(로그인·시스템 제외) 최근 10건을 한 줄로 흘린다(마우스를 올리면 멈춤). 새 이벤트가 오면 "새 이벤트 N" 표시. **펼치기**를 누르면 위로 목록 패널이 열리고(구분 칩 필터), 행을 누르면 이벤트 상세 팝업.
- **갱신 주기**: 장비 상태 5초(바뀐 경우에만 다시 그리고 지구별 스크롤 유지) / 이벤트 5초(`since` 폴링) / 시스템 정보 30초.
- **작은 화면**: 폭 1600px 이하에서 배지·칩 간격을 줄이고 필터 칩은 줄바꿈하지 않는다. 서버 상태 목록은 높이가 모자라면 카드 안에서 스크롤한다. 높이 860px 이하(1366×768)에서 도넛·카드·행 간격을 줄여 한 화면에 맞추고, 720px 이하에서는 한 단계 더 줄인다(그래도 모자라면 서버 상태 목록만 스크롤).

### 3.1 장비 실시간 화면

실시간 현황의 장비 리스트에서 행을 클릭하면 전환되는 장비 단위 상세 화면. **좌측(요약·제어) : 우측(데이터)**로 나눈다.

**좌측**

- **장비명 등 기타 설명** — 장비명, 지역·시설동, 운영 상태
- **가동율** — 해당 장비의 운전 비율 (`GET /api/equipments/{id}/utilization`)
- **운전상태** — 해당 장비의 운전 상태
- **압축기 구성** — 소속 압축기별 IP/MAC 주소 목록 (통신/경보 상태는 우측 실시간 리스트에서만 표시 — 같은 정보를 두 군데서 중복 표시하지 않음)
- **비상정지 카드** — 장비 단위 비상정지/해제(75·76번 API, DO 출력이 장비 비상정지 회로에 물려 있어 압축기 한 대만 따로 멈출 수 없다). **시스템관리자·안전관리총괄자·안전관리책임자에게만 보인다**(실제 차단은 서버 403). 정지는 재확인 팝업 안에서 **로그인 비밀번호**를 받아 서버가 검증하고(틀리면 400 → 입력칸에 안내), 해제는 비밀번호 없이 재확인만 한다. 비상정지 중이면 카드가 빨간 면으로 바뀌고 장비명 옆·실시간 현황 장비 행에 빨간 "비상정지" 배지가 붙는다(10초 갱신 — 현장 패널에서 직접 누른 경우도 반영).

**우측** (위에서 아래로 세로 배치 — 화면 높이에 가두지 않고 페이지 전체가 스크롤된다. **좌측은 우측 스크롤과 상관없이 제자리에 고정**되고, 화면보다 길면 좌측 안에서만 스크롤된다)

- **압축기 리스트** — 컬럼 순서는 **압축기 | 저온 ~ 운전전류(채널 7개, 머리글은 채널번호 없이 "채널명 (단위)" 한 줄) | 통신 상태**. 채널값은 3초, 통신 상태는 10초 주기 갱신. 압축기별 경보 상태 컬럼은 없고, **장비 기준 경보 상태를 좌측 장비명 아래(운영 상태 옆)에 "정상" / "경보발생" / "통신 불량" 배지**로 보여준다(장비 `hasAlarm`, 10초 갱신). **통신이 끊기면 백엔드가 `hasAlarm`을 항상 false로 내리므로**(백엔드 변경 2026-09-28) 통신 상태를 먼저 보고 "통신 불량"으로 표시한다 — 그러지 않으면 "경보 없음"과 "통신이 끊겨 알 수 없음"이 똑같이 "정상"으로 보인다. 행을 누르면 아래 트렌드가 그 압축기로 바뀌고, 그 행에 강조 표시가 붙는다.
- **압축기 트렌드 / 운전 상태 타임라인 / 이벤트 이력** — [4장 자료 조회](#4-자료-조회)와 **같은 공통 컴포넌트**를 쓴다(아래 "트렌드·이벤트 공통 컴포넌트" 참고). 화면 모양과 동작(확대·이동, 채널 선택·숨기기, 경보 구간, 이벤트 필터·상세 팝업)이 자료 조회와 똑같다.
    - 날짜를 바꿔 지난 날도 볼 수 있다. 기본은 오늘이다.
    - **오늘을 보고 있으면 자동으로 다시 불러온다** — 이벤트 10초, 트렌드·가동율 60초 주기("실시간 갱신 중" 표시). 트렌드 기록이 분 단위라 더 자주 받아도 달라지는 게 없다. 다시 그려도 보던 시간 구간·선택 채널·숨긴 채널·이벤트 필터는 그대로다.
    - 이벤트는 장비·날짜 전용 API(58번)를 쓴다. 예전에는 전체 이벤트 200건(9번)을 받아 이 장비 것만 걸렀는데, 다른 장비 이벤트가 많으면 이 장비 것이 잘려 나갔다.

## 4. 자료 조회

**장비 한 대의 하루**를 보는 조회 전용 화면이다(수정할 항목이 없다). 전용 API 하나가 아니라 네 개를 조합해서 구성한다 — 압축기 목록(3번), 압축기별 하루 트렌드(6번), 그날 가동율(7번), 그날 이벤트(58번).

**위에서 아래로 5단 구성**이다. 1,440분짜리 그래프가 주인공이라 조회 조건을 좌측 세로가 아니라 상단 가로 한 줄에 둔다.

1. **조회 조건** — 지역 → 시설동 → 설비, 날짜(◀ ▶로 하루씩 이동), 조회 버튼. 이미 조회한 뒤 날짜를 옮기면 바로 다시 조회된다.
2. **요약 타일** — 가동율 / 기록된 시간 / 경보 건수 / 압축기 수. 가동율의 분모는 "실제 기록이 있는 분"이라 기록이 빈 구간이 있으면 수치가 왜곡돼 보이므로, 기록된 시간을 나란히 보여준다. 가동율·기록된 시간은 게이지 막대로, 경보는 발생/해제 건수 배지로도 보여준다.
3. **압축기 트렌드** — 압축기를 탭으로 전환한다(트렌드 API가 압축기 단위이고, 여러 대를 한 그래프에 겹치면 읽을 수 없다). 그래프는 [3.1장](#31-장비-실시간-화면)과 같은 방식(7채널 동시 표시, 채널마다 별도 y축, 선택한 채널만 강조·눈금 표시, 가로축 00:00~23:59 고정)에 더해 **통신장애 구간은 회색 빗금, 경보 구간(발생~해제)은 붉은 그라데이션 음영**으로 표시한다. 선택한 채널은 선 아래를 채널 색 그라데이션으로 채우고, 세로축 위에 단위를 표시한다. 그래프 아래 채널 카드에는 마우스 위치의 값과 그날 추이 미니 그래프(10분 평균)가 나온다.
4. **운전 상태 타임라인** — 보고 있는 압축기의 통신장애·경보 구간을 하루 전체 한 줄 막대로 보여준다. 그래프를 확대해도 막대는 하루 전체 그대로이고, 지금 그래프에 보이는 구간을 파란 테두리로 표시한다. 그래프 음영 범례는 여기에 있다.
5. **이벤트 이력** — 순번·내용·구분·시각 표. 카테고리 칩(건수 표시)으로 거를 수 있고, 내용을 클릭하면 상세 팝업이 열린다. 채널이 있는 이벤트는 내용 앞에 그래프 선 색의 채널 태그가 붙고, 경보 해제는 초록 "경보 해제" 배지로 구분한다. 경보는 그 시점의 측정값과 정상 범위를 실제값으로 변환해 보여준다(서버가 raw 값·단위·소수점을 스냅샷으로 함께 내려줌).

트렌드·타임라인·이벤트 표는 [3.1장](#31-장비-실시간-화면)과 공유하는 공통 컴포넌트다. 화면 디자인(2026-09-17 개편 — 옅은 파랑·보라 그라데이션 배경 위 흰 카드, 파랑→보라 그라데이션 강조색)은 같은 날 **앱 전체**로 넓혀 `common/css/common.css`의 토큰·카드·버튼·표·배지·칩·세그먼트·요약 타일(`.stat-tile`)에 반영했다.

경보 이벤트는 발생과 해제가 짝으로 기록되므로, 그 쌍을 이어 그래프의 경보 구간을 그린다. 짝이 없으면(자정을 넘겨 지속 중이거나 전날부터 이어진 경보) 구간을 화면 끝까지 열어둔다.

## 5. 공지사항

전사 공지 게시판. **결재가 없는 가장 단순한 문서**이고 장비와도 무관하다 — 교육훈련([8장](#8-교육훈련))에서 결재만 뺀 구조라 화면 구성도 같다(목록 페이지 + 상세 모달). 백엔드 API가 구현되어 있다([api-manual.md 51~57번](reference/api-manual.md)).

- 항목: **제목**(필수), 내용, 첨부파일. 작성자·작성일시는 서버가 자동으로 기록한다.
- 목록 컬럼은 순번 / 제목 / 작성자 / 작성일 / 첨부다. **상단 고정 공지는 항상 맨 위에 오고 제목 앞에 "📌 고정" 배지**가 붙는다. 고정 공지는 작성 순서와 어긋나므로 순번을 매기지 않고 `-`로 표시한다.
- 권한: 조회·등록은 로그인한 누구나, **수정·삭제·첨부 변경은 작성자 또는 시스템관리자**(서버가 `canEdit`/`canDelete`로 내려줌), **상단 고정/해제는 시스템관리자만**(전용 API라 응답에 플래그가 없고 역할로 판단한다).

## 5-1. 일괄 결재 (상단바 결재 알림)

결재가 필요한 문서를 화면마다 찾아 들어가지 않고 한곳에서 처리한다(2026-09-28). 상단바 사용자 정보 왼쪽에 **벨 아이콘 + 대기 건수 배지**가 뜨고, 누르면 일괄 결재 팝업이 열린다.

- **배지**: `GET /api/approvals/pending/count`(73번)를 **60초마다** 호출한다. 목록까지 받으면 낭비라 건수만 받는다. 탭이 보이지 않으면 갱신하지 않는다. **결재할 게 0건이면 벨 자체를 숨긴다** — 결재 대상이 아닌 역할(시스템관리자·일반관리원)은 항상 0건이라 아무것도 보이지 않는다.
- **팝업**: 열 때 `GET /api/approvals/pending`(72번)으로 문서 그룹과 목록을 받는다. 좌측은 문서 그룹(점검일지·운전일지·교육훈련·수리일지, 건수 표시 / 0건은 흐리게), 우측은 그 그룹의 목록이다. 그룹 이름은 서버가 주는 `label`을 그대로 쓴다 — 결재 문서 종류가 늘어도 프론트를 고치지 않는다.
- **목록 한 줄**: 문서명(장비명 또는 제목) · 위치(수리일지는 제목까지 붙는다) · 일자. 점검일지·운전일지는 작성자가 없다(서버가 자동 생성/이어채움하는 문서라 `authorName`이 `null`).
- **결재**: 체크 후 "선택 항목 결재" → `POST /api/approvals/bulk`(74번). **한 번에 한 문서 그룹만** 보낸다. 그룹을 바꾸면 선택이 초기화된다.
- **부분 실패**: 건별로 성공/실패가 오므로(74번) 성공 건수와 실패 사유를 함께 알려주고 목록을 다시 불러온다 — 실패한 것만 목록에 남는다.
- **일괄 취소는 없다** — 되돌리는 동작이라 문서별 단건 취소만 지원한다(백엔드 사양).
- 화면: `common/js/approval-inbox.js`(팝업·배지), 상단바 버튼은 `common/js/layout.js`, 스타일은 `common.css`. 시안 `mokup/bulk_approval_v1.html`.

## 6. 조직 관리

안전관리 인원의 조직도와 인원 관리 화면이다. 백엔드 API는 [api-manual.md 59~69번](reference/api-manual.md)(사양: [reference/Organization/README.md](reference/Organization/README.md)).

**첫 화면 — 조직도** (로그인한 누구나)

- **선임(`isAppointed`)이면서 활성 계정인 인원만** 담당업무 단계별로 위에서 아래로 보여준다: 안전관리총괄자 → 안전관리책임자 → 안전관리원 → 일반관리원. 단계 사이는 세로 연결선으로 잇고(인원 간 상하 관계 데이터는 없어 단계 단위로만 표현), 인원이 없는 단계는 생략한다. 미선임·비활성 인원은 조직도에 나오지 않고 관리 모달에서만 보인다.
- 인원 카드: **담당업무(강조 배지, 단계별 색)**, 소속팀, 성명(직위는 이름 옆에 작게), 연락처1·2, 선해임 신고서 받기 아이콘(파일이 없으면 흐리게), 세부정보 버튼.
- **세부정보 팝업**: 사용자 ID를 뺀 전체 정보와 선해임 신고서(파일명 클릭으로 받기), 담당장비(지역 → 시설동으로 묶고 시설동마다 장비명을 한 줄로 나열, 건수 표시).

**관리 모달** (시스템관리자에게만 "관리" 버튼 노출) — 장비 관리의 수리일지 팝업과 같은 좌우 분할

- **좌측**: "+ 신규 인원", 이름 검색, "비활성 인원 포함"(기본 꺼짐), 인원 목록(성명 + 담당업무 배지, 미선임·비활성 태그).
- **우측 폼**: 계정(사용자 ID — 신규는 중복확인 필수·비밀번호 2번 입력, 수정은 ID 읽기 전용·비밀번호 초기화 버튼·활성/비활성) / 인적사항(성명*, 소속팀, 직위, 담당업무*, 연락처1·2, 대직자, 선임여부, 선해임 신고서, 법정교육일, 차기교육일) / 담당장비(지역·시설동으로 묶은 체크 목록 — 시설동 단위 전체 선택, 펼치기, 장비명·시설동 검색, "선택 N대 / 전체 M대").
- 담당업무를 바꾸면 "결재 권한도 함께 바뀝니다" 경고를 보여준다. 비활성으로 바꾸면 "이미 로그인한 경우 최대 12시간 계속 사용 가능" 경고와 저장 시 확인 창을 띄운다(삭제 API는 없고 비활성화만 있다).
- 선해임 신고서는 고른 파일을 **저장할 때** 올린다(신규 인원은 저장 전 사용자 id가 없다). 교체·삭제도 저장 시 반영된다.
- 저장하지 않은 변경이 있으면 다른 인원을 고르거나 모달을 닫을 때 확인한다.

일반 사용자의 본인 연락처·비밀번호 변경("내 정보")은 이 페이지와 무관하며 추후 작업 예정이다.

## 7. 장비 관리


> **목록 범위(2026-09-28)**: 장비 목록은 `GET /api/equipments?mine=true`로 **담당 장비만** 받는다 — 수정 권한이 담당 기준이라 목록도 같은 기준으로 맞춘다. 시스템관리자는 `mine=true`여도 서버가 전체를 주므로 프론트에서 역할을 분기하지 않는다. 담당 장비가 없는 사용자에게는 "담당 장비가 없습니다. 시스템관리자에게 담당 장비 등록을 요청하세요."를 보여준다. 점검일지·운전일지의 장비 선택 목록도 같다(자료 조회·실시간 현황은 전체 대상이라 그대로).
장비 속성(약 40여 개 필드)·압축기·채널 설정을 조회/등록/편집하는 관리자용 화면이다. 실시간 감시 화면([3.1장](#31-장비-실시간-화면))과 역할이 분리되어 있어, 통신 상태·경보처럼 시시각각 바뀌는 값은 이 화면에 두지 않는다. 이 화면이 쓰는 백엔드 API는 전부 구현되어 있다([api-manual.md 1~5-1, 21~42번](reference/api-manual.md)).

**좌측 — 필터 + 등록**

- 지역 / 시설동 / 상태 select(전체 포함) + 장비명 검색
- "+ 신규 등록" 버튼 — 장비 속성과 함께 압축기 IP/MAC 목록을 최소 1개 이상 입력해야 등록된다. **압축기는 이 등록 시점에만 개수를 정할 수 있고, 이후에는 추가·삭제가 불가능하다**(API 자체가 지원하지 않음) — 등록 화면에 이 사실을 경고 문구로 안내한다.

**우측 — 목록**

목록 컬럼은 **위치(지역·시설동·위치 통합) / 장비명 / 관리번호 / 상태 / 압축기 / 검사이력 / 수리일지** 7개다. 행 전체가 아니라 **장비명을 클릭해야 장비 상세 모달이 열린다** — 압축기/검사이력/수리일지는 각자 컬럼의 배지(`COMP#N`, "검사이력", `N건`)를 클릭하면 장비 모달을 거치지 않고 바로 해당 팝업이 열린다. 검사이력은 장비별 개수를 한 번에 알려주는 API가 없어 배지에 숫자를 넣지 않는다(눌러서 팝업을 열면 그 안에서 바로 확인 가능).

- **장비 상세 모달**: 좌(위치/상태·운전 임계값·세부설정 버튼) / 우(사업소 실물 "장비 이력 카드" 서식을 그대로 재현한 표 — 모델명/제조사, 냉동능력, 압축기·냉각탑 사양, 응축기/증발기 형식, 설계압력/정격전압, 안전밸브, 기타사항, 장비 사진·설치 위치도 업로드 슬롯 각 1장) 2단 구성이다. "삭제" 개념은 없다 — 상태 select에서 "철거"를 고르고 저장하면 된다(기존 이력 데이터는 그대로 남는다). 운전 임계값은 raw가 아니라 실제값으로 보여주고 입력받는다(1번 압축기 CH07의 소수점 자리수를 서버가 계산해 응답에 함께 내려줌). 장비 사진/설치 위치도는 파일 선택 즉시 업로드되고(같은 슬롯에 다시 올리면 덮어씀), 신규 등록 화면에서는 장비를 먼저 저장해야 올릴 수 있다.
    - **냉각수·브라인·전압 설정**("세부설정" 버튼, 좌측 맨 아래)은 이 모달과 완전히 분리된 별도 팝업으로 관리한다. 운전일지가 이 값을 근거로 실측값처럼 보이는 랜덤값을 자동 생성하기 때문에, 일반 설정 화면 어디에도 노출하지 않는다(사용자 요구사항).
- **압축기 구성 팝업**: 좌측 순번 리스트(`COMP #1`, `COMP #2`, …, `sequenceNo` 오름차순) + 우측 상세(IP/MAC/순번, CH01~07 채널 설정)로 구성된 마스터-디테일 화면이다. 순번은 조회만 가능하고 수정할 수 없다. 채널 설정(사용 여부/명칭/단위/소수점 자리수/경보사용/경보하한·상한/경보 발생·해제 지연시간)은 명시적 "저장" 버튼을 눌러야 반영되며, 저장하지 않은 채 다른 압축기를 고르거나 팝업을 닫으려 하면 확인을 한 번 더 받는다. 경보하한이 경보상한보다 큰 값은 저장 시 거부한다(판정 로직이 깨지기 때문).
- **장비 검사이력**([9장](#9-점검일지) 점검일지 `InspectionReport`와는 무관한 별개 기능 — 장비 이력카드에 딸린, 실시한 검사/점검을 자유 형식으로 남기는 게시판이다): 압축기 구성 팝업과 같은 **좌(목록) · 우(상세) 마스터-디테일** 화면이다. 좌측 목록엔 일시·제목·비고 미리보기와 첨부파일 개수(📎), 우측엔 날짜·제목·검사내용·비고·첨부파일을 세로로 배치한다. 저장 안 한 변경사항이 있는 채로 다른 항목을 고르거나 팝업을 닫으면 확인을 받는다(압축기 팝업과 동일한 패턴). 조회·작성은 로그인한 누구나 가능하고, **수정은 작성자 본인 또는 시스템관리자만**(2026-09-16 사양 추가), **이력 레코드 삭제는 시스템관리자만** 가능하다. 수정 권한은 서버가 계산해 응답의 `canEdit`(boolean)으로 내려주므로 프론트는 그 값만 보고 폼을 읽기 전용으로 바꾼다. **첨부파일 추가·삭제는 수정 권한과 같은 기준**(= `canEdit`)으로 버튼을 노출한다 — 첨부파일 API 자체엔 권한 검사가 없어(로그인만 하면 남의 이력에도 올릴 수 있다) 이 제한은 프론트 판단이다. 파일당 10MB 제한은 선택 즉시 프론트에서 1차로 거른다. 신규작성 후 저장하면 그 자리에서 편집 화면으로 이어져 바로 첨부파일을 추가할 수 있다(첨부는 레코드가 저장돼야 가능하기 때문). 백엔드 API가 실제로 구현되어 있다(api-manual.md 26~34번).
- **수리보수 및 철거일지**: 검사이력과 같은 **좌(목록) · 우(상세) 마스터-디테일** 화면이다. 우측은 사업소 실물 양식을 그대로 옮긴 표(제목 / 일시 · 수리보수 및 철거장소 / 수리보수 및 철거자 · 수리보수 및 철거대상 / 전의 상태 · 후의 상태 · 후 검사 및 시험결과 3열 / 고장원인 / 고장방지대책 / 종합의견)이고, 그 위에 결재란이 놓인다. 좌측 목록에는 일시·작성자·제목과 함께 **책임자 결재 대기 / 총괄자 결재 대기 / 완료** 배지를 표시한다.
    - 결재는 **안전관리원이 "해당없음"(`/`)** 이라 실제 승인은 안전관리책임자 → 안전관리총괄자 2단계다([12장](#12-결재-시스템-공통-규칙)).
    - **한 단계라도 승인되면 수정이 완전히 잠긴다**(서버가 `409`). 삭제는 그때부터 시스템관리자만 가능하며, 잠금을 풀려면 시스템관리자가 결재를 리셋해야 한다. 수정·삭제 가능 여부는 서버가 계산해 응답의 `canEdit`/`canDelete`로 내려준다.
    - 일시는 날짜만 입력받는다(실물 양식 기준). 서버는 UTC로 저장하므로 화면에서 한국시간 날짜로 변환해 보여준다.
    - **첨부파일은 지원하지 않는다**(사양 변경 — [13장](#13-첨부파일-공통-규칙) 대상에서 제외됨). 백엔드 API가 실제로 구현되어 있다(api-manual.md 35~42번).

## 8. 교육훈련

안전 교육·훈련 실시 내역을 기록하고 결재를 받는다. **다른 결재 문서(점검일지/운전일지/수리일지)와 달리 장비에 매달리지 않는 전사 문서**라 장비 선택이 없다. 백엔드 API가 구현되어 있다([api-manual.md 43~50번](reference/api-manual.md)).

- 항목: **제목**, 일시(날짜), 장소, 강사, 교육내용, 참석자 명단(단순 문자열로 저장 — 시스템 등록 인원과 무관), 첨부파일. 제목과 일시만 필수다.
- **화면 구성**: 목록 페이지 하나 + 항목 클릭 시 상세 모달. 장비별 문서가 아니라 목록 API에 필터가 아예 없어(건수가 적어 페이징도 없음) 좌측 선택 영역이 필요 없다. 목록 컬럼은 일시 / 제목 / 장소 / 강사 / 첨부 / 결재상태이고, 결재상태는 **책임자 결재 대기 / 총괄자 결재 대기 / 완료** 3가지다.
- 결재 시스템: 안전관리원(해당 없음, `/` 표시 — 결재 불가) → 안전관리책임자 결재 → 안전관리총괄자 결재 ([12장](#12-결재-시스템-공통-규칙)).
    - **이 문서만의 예외 — 승인 시 담당 장비를 검사하지 않는다.** 검사할 장비가 없어 역할만으로 판정하므로, 안전관리책임자·총괄자면 누구나 결재할 수 있다.
    - **한 단계라도 승인되면 문서 수정은 물론 첨부파일 추가·삭제까지 막힌다**(서버가 `409`). 삭제는 그때부터 시스템관리자만 가능하고, 잠금을 풀려면 시스템관리자가 결재를 리셋해야 한다. 수정·삭제 가능 여부는 서버가 `canEdit`/`canDelete`로 내려준다.
- 일시는 날짜만 입력받는다. 서버는 UTC로 저장하므로 화면에서 한국시간 날짜로 변환해 보여준다(수리일지와 동일).

## 9. 점검일지

장비별로 점검일지를 작성한다. **점검일지 1건 = 1주일(일요일~토요일)** 동안의 항목별 점검 데이터를 의미한다. (추후 최종 UI는 캘린더 형태로 작성 예정)

백엔드 API가 구현되어 있다 ([api-manual.md 11~15번](reference/api-manual.md)) — `GET /api/inspection-items`, `GET`/`PUT /api/inspection-logs`, 결재 3종(`approve`/`approve/cancel`/`approvals/reset`).


**PDF 저장** — 열려 있는 점검일지 1건을 A4 가로 PDF로 저장한다(모달 하단 "PDF 저장", 2026-09-29 엑셀 저장 대체). 브라우저 인쇄 창에서 대상 "PDF로 저장"을 고르면 파일이 되고 프린터를 고르면 종이로 나온다. **결재가 끝난 문서만** 저장할 수 있고(진행 중이면 버튼 비활성), 저장 전 주차엔 버튼이 없다. 문서 머리(제목·지역·시설동·장비명·점검기간 + 결재란) · 점검표(화면과 같은 묶음, O / X 모양) · 점검자 의견 · 안내문 · 출력 일시/출력자. 공통 모듈 `common/js/pdf-export.js` + `common/css/pdf-export.css`.

**좌측 — 작성 장비 선택창**

- 지역 선택: A지구 / B지구 / C지구
- 시설동 선택
- 설비(장비명) 선택
- **날짜 선택 (주 단위, 반드시 일요일 시작)** — API의 `weekStart` 파라미터가 일요일이 아니면 `400` 오류이므로, "이전 주 / 다음 주" 이동 방식으로 항상 유효한 일요일 날짜만 고르게 한다. (예: "8월 첫째 주" 같은 표시는 유지하되, 내부적으로 넘기는 값은 항상 그 주의 일요일 날짜.)

**우측 — 콘텐츠 표시부**

- 선택된 장비·주차의 점검일지 조회 / 작성 (`GET /api/inspection-logs?equipmentId=&weekStart=`). **저장된 적 없는 주차도 오류가 아니라 빈 폼으로 내려온다** — 프론트는 이 응답을 그대로 "새로 작성" 화면으로 그리면 된다.
- 결재 시스템: 안전관리원 → 안전관리책임자 → 안전관리총괄자 (3단계 전부 실사용, [12장](#12-결재-시스템-공통-규칙) 참고). **결재가 하나라도 진행되면 이 화면은 읽기 전용으로 전환**되어야 한다(서버가 `PUT`을 `409`로 막는다).
- 사용자는 각 점검 항목에 대해 요일별 점검 결과를 `O` / `/` / `X`로 기록하고, 항목별로 메모를 남길 수 있다. **저장은 매번 10개 항목 전체를 다시 보내는 방식**이다(부분 수정 불가) — 프론트는 항상 폼 전체 상태를 들고 있다가 통째로 전송한다.

### 점검 항목 표 (양식)

## 10. 운전일지


> **결재 후 수정 제한(2026-09-28 확정)**: 결재가 하나라도 진행되면 읽기 전용이다 — 점검일지와 같은 규칙이며, 결재가 필요한 문서 전체의 공통 규약이다. 백엔드는 운전일지 저장을 막지 않으므로(api-manual 18번) 화면에서 잠근다. 다시 수정하려면 시스템관리자의 결재 리셋이 필요하다.
장비별로 운전일지를 조회 / 작성한다. 백엔드 개발 1차 완료 — API 문서([api-manual.md 16~20번](reference/api-manual.md))에 더해, 실제 백엔드 소스코드가 [reference/OperationReport/](reference/OperationReport/README.md)에 함께 제공되어 세부 규칙까지 확정할 수 있었다. `GET`/`PUT /api/operation-logs`, 결재 3종.

> **2026-09-11 사양 변경**: 항목 자동화 방식이 "채널 자동측정 7개 + 사용자 직접입력 9개" 2갈래에서 **"채널 자동측정 5개 + 장비설정 기반 랜덤값 5개 + 사용자 직접입력 6개" 3갈래**로 바뀌었다. `냉각수온도(입구)/(출구)`가 더 이상 CH01 채널을 읽지 않고, `브라인온도(입구)/(출구)`·`운전전압`과 함께 새로 추가된 [`Equipment`의 냉각수/브라인/전압 설정](reference/Eqmt.md)(유무 + min/max) 기반 랜덤값으로 바뀌었다. 아래 내용 전체가 이 최신 사양 기준이다.


**PDF 저장** — 열려 있는 운전일지 1건을 A4 세로 PDF로 저장한다(모달 하단 "PDF 저장", 2026-09-29 엑셀 저장 대체). 규칙은 점검일지와 같다(결재 완료 문서만, 인쇄 창에서 "PDF로 저장"). 표는 화면과 같은 `buildReportRows`로 만들어 **압축기 수(최대 6대)에 따라 행이 늘고 줄어도** 모양이 같다 — 압축기 1대는 1쪽, 6대는 2쪽. 쪽은 계통(구분) 경계에서 나뉘고 표 머리글이 쪽마다 다시 찍힌다(한 쪽보다 긴 냉매계통만 행 단위로 나뉨). 시안 `mokup/operation_pdf_v1`.

**좌측 — 작성 장비 선택창**

- 지역 선택: A지구 / B지구 / C지구
- 시설동 선택
- 설비(장비명) 선택
- 날짜 선택 (일 단위)

**우측 — 콘텐츠 표시부**

- 선택된 장비·날짜의 운전일지 조회 / 작성 (`GET /api/operation-logs?equipmentId=&date=`). 저장된 적 없는 날짜도 오류가 아니라 빈 폼(`id: null`, `items`/`references` 빈 배열)으로 내려온다. 다만 자동 기록 서비스가 장비 등록 시점부터 매일 돌기 때문에, 정상 운영 중이라면 오늘/과거 날짜는 거의 항상 실제 데이터가 있다.
- 결재 시스템: 안전관리원 → 안전관리책임자 → 안전관리총괄자 (점검일지와 동일한 3단계, [12장](#12-결재-시스템-공통-규칙) 참고).
- **점검일지와 달리, 결재가 진행 중이어도 저장(`PUT`)이 막히지 않는다.** 결재 완료 후 수정을 막을지는 백엔드가 의도적으로 강제하지 않는다("사양 변경 가능성이 있어 백엔드에 강하게 고정하지 않기로 함") — 화면에서 판단해서 처리해야 하는, 아직 열려 있는 설계 결정이다 ([11장](#11-확인이-필요했던-부분-결정-사항) 참고).
- **항목 목록의 이름·구분(냉매계통/냉수계통/전기계통/기타 같은 그룹)·순서는 백엔드가 관리하지 않는다** — 프론트가 정의하는 "레포트 형식"이다. 아래 [운전일지 양식](#운전일지-양식)이 그 정의다. 단, **자동으로 채워지는 10개 항목**(채널 자동측정 5개 + 장비설정 기반 랜덤값 5개, [자동화 동작](#자동화-동작) 참고)의 `itemKey` 문자열만은 백엔드 자동화 로직과 정확히 일치해야 한다.
- `PUT`은 항상 **전체 교체**다 — 문서 하나 저장할 때 `items`/`references` 배열 전체를 매번 다시 보낸다(점검일지와 동일한 방식).

### 자동화 동작

운전일지는 하루 4개 고정 시각(09:00 / 13:00 / 16:00 / 21:00 KST, 전 장비 공통)마다 항목값을 기록하며, 16개 표시 항목은 **세 갈래**로 자동화 방식이 다르다. 판정은 항상 아래 **우선순위 규칙**을 먼저 적용한 다음, 해당하지 않으면 각 그룹 규칙을 따른다.

**우선순위 규칙 (전체 공통)**

1. **장비가 운영 중이 아니면**(장비 `status`가 미운영/철거/사용중지 중 하나이거나 `communicationStatus`가 연결됨이 아님) **그 장비의 16개 항목 전부가 무조건 `/`다.** 아래 2~4번보다 우선하며, 사용자 직접입력 항목의 "마지막 입력 이어받기"(아래 C번)도 이 규칙 앞에서는 무시되고 `/`로 강제된다.
2. **장비가 운전 중이 아니면**(`GET /api/equipments`의 `isRunning: false`) **채널 자동측정 + 장비설정 기반 랜덤값(아래 A, B) 항목만 `/`다.** 사용자 직접입력(C) 항목은 운전 여부와 무관하게 그대로 이어받는다.
3. 위 1~2번에 해당하지 않으면 아래 A/B/C 그룹별 규칙을 따른다.

**A. 채널 자동측정 (5개)** — 조건을 통과하면 그 시각 압축기 채널값으로 **항상 덮어쓴다**(사용자가 미리 입력해놨어도 무시됨). 통신 불가·읽기 실패 시 `/`. 정확한 매핑은 백엔드 `AutoMeasuredItemCatalog`에 고정되어 있다:

| itemKey      | 채널 | 압축기별 반복 |
| ------------ | ---- | ------------- |
| 토출압력     | CH05 | 예            |
| 토출가스온도 | CH02 | 예            |
| 흡입압력     | CH04 | 예            |
| 오일압력     | CH06 | 예            |
| 운전전류     | CH07 | 아니오        |

- "압축기별 반복" 4개(토출압력/토출가스온도/흡입압력/오일압력)는 압축기 수만큼 항목이 생겨 각각 표시된다(`compressorId` 있음).
- 운전전류는 **장비당 1개**뿐이며(`compressorId: null`), 항상 그 장비의 **SequenceNo가 가장 작은(1번) 압축기** 값을 사용한다.

**B. 장비설정 기반 랜덤값 (5개) — 사양 변경으로 신규, 채널을 읽지 않는다** — `냉각수온도(입구)`/`냉각수온도(출구)`/`브라인온도(입구)`/`브라인온도(출구)`/`운전전압`. 예전엔 냉각수온도가 CH01을 그대로 읽었지만, [`Equipment`에 냉각수/브라인/전압 각각의 "유무" + "정상범위(min/max)" 속성](reference/Eqmt.md)이 생기면서 채널이 아니라 **장비 설정을 기준으로 값을 만든다.**

| itemKey          | 소스 (`Equipment` 속성)                             |
| ---------------- | --------------------------------------------------- |
| 냉각수온도(입구) | `HasCoolingWater` + `CoolingWaterInletMin/Max`      |
| 냉각수온도(출구) | `HasCoolingWater` + `CoolingWaterOutletMin/Max`     |
| 브라인온도(입구) | `HasBrine` + `BrineInletMin/Max`                    |
| 브라인온도(출구) | `HasBrine` + `BrineOutletMin/Max`                   |
| 운전전압         | `HasVoltage` + `VoltageMin/Max` (입/출구 구분 없음) |

- 그 장비가 해당 항목을 "사용 안 함"(`Has* = false`)이거나 min/max 중 하나라도 설정 안 됐으면 `/`.
- "사용함"이고 min/max가 있으면 그 사이의 랜덤값을 **소수점 1자리로 반올림**한 문자열로 저장한다 (예: `100`→`100.0`, `12.345`→`12.3`. 단순 반올림이며 raw 스케일 변환이 아니다). `min=max=0`처럼 둘 다 `0`이어도 유효한 범위로 보고 `0.0`을 기입한다.
- 전부 **장비당 1개**다(`compressorId: null`) — 압축기와 무관하다.

**C. 사용자 직접입력 (6개)** — `냉매량`/`오일량`/`단자대&판넬상태`/`드레인상태`/`저압부단열재상태`/`이상진동및소음상태`. 빈 칸일 때만 직전 값을 이어받는다(이미 입력된 값은 절대 덮어쓰지 않음). 이 이어받기는 하루 안(9→13→16→21)은 물론 **날짜 경계도 넘어 무기한 이어진다** — 단, 위 우선순위 1번(장비 비운영)에 해당하면 이 이어받기도 무시되고 `/`로 강제된다.

기준값(`references`)도 항목값과 같은 방식으로 이어받는다: 빈 칸일 때만 직전 로그의 값을 그대로 물려받고, 시스템이 임의로 초기값을 만들어 채우는 일은 없다.

**공통**: 운전일지는 **절대 누락되지 않는다** — 장비를 등록한 순간부터 매일 자동으로 로그가 생성된다 (점검일지가 "사용자가 최초 1회 작성해야 그 뒤로 자동 이어채우기가 시작"되는 것과 반대 정책).

### 기준값(실측 기준)

- **16개 표시 항목 전부가 기준값을 갖는다** (O/X 항목도 예외 없이) — 다만 냉각수온도/브라인온도는 입구·출구가 기준값 하나를 공유하므로, 실제 기준값 키(`references`)는 `16 - 2 = 14개`다: 토출압력·토출가스온도·흡입압력·오일압력·냉매량·오일량·냉각수온도·브라인온도·운전전압·운전전류·단자대&판넬상태·드레인상태·저압부단열재상태·이상진동및소음상태.
    > 이전 버전에서는 O/X류 항목(냉매량/오일량/단자대&판넬상태/드레인상태/저압부단열재상태/이상진동및소음상태)에 기준값이 없다고 잘못 적었었다 — 백엔드 소스([reference/OperationReport/README.md](reference/OperationReport/README.md) "기준값" 절)의 실제 예시 표를 보면 이 항목들도 "(기준값 참고)"로 기준값을 갖는다. 아래 표에서 정정.
- 기준값은 **문서(그 장비·그 날짜의 로그)마다 스냅샷으로 저장**된다 — 나중에 기준값을 바꿔도 이미 저장·결재된 과거 문서의 값은 그대로 유지된다. 새 문서를 만들 때는 그 장비의 가장 최근 문서에 저장돼 있던 기준값을 그대로 복사해오는 방식(위 "사용자 직접입력 항목 이어받기"와 같은 매커니즘)이다.
- 기준값은 사용자가 자유롭게 입력/수정하는 텍스트(`referenceText`)이며 프론트가 검증하지 않는다.

### 운전일지 양식

프론트가 정의하는 레포트 형식(항목 목록·구분·순서)이다. "구분" 열은 백엔드에 저장되지 않는 화면 표시용 그룹. 총 16개 표시 행, 그 중 냉각수온도·브라인온도가 입/출구 쌍으로 기준값을 공유해 **기준값 키는 14개**다.

| 구분     | 점검항목           | 실측 기준           | 자동화                                                                           |
| -------- | ------------------ | ------------------- | -------------------------------------------------------------------------------- |

### 레포트 표 레이아웃 (rowspan 병합)

모달 표는 사업소 제공 실물 양식(스캔 이미지 기준)과 동일하게, 공통 값을 갖는 열을 **행 병합(rowspan)** 해서 보여준다. 점검일지의 "번호/점검항목" 병합([9장](#9-점검일지))과 같은 원리이되, 운전일지는 2단계로 겹쳐서 병합된다.

| 열                                      | 병합 단위                                                                                     | rowspan 값                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 구분 (냉매계통/냉수계통/전기계통/기타)  | 계통 그룹 전체                                                                                | 그 계통에 속한 모든 행 수 (아래 계산식 참고) |
| 사용장비 (그 계통의 모니터링 시스템명)  | 구분과 항상 동일하게 묶임                                                                     | 구분과 같은 값                               |
| 점검항목 (토출압력 등 항목명)           | 압축기별 반복 항목은 압축기 수만큼, 입/출구 쌍 항목(냉각수온도·브라인온도)은 2, 단일 항목은 1 | 가변                                         |
| 실측 기준                               | 점검항목과 항상 동일하게 묶임                                                                 | 점검항목과 같은 값                           |
| 압축기#N 라벨 / 입구·출구 라벨          | 병합 없음                                                                                     | 매 행 1                                      |
| 09:00 / 13:00 / 16:00 / 21:00 실측값 셀 | 병합 없음                                                                                     | 매 행 1                                      |

계통 그룹의 총 행 수는 그 장비의 **압축기 대수(N)**에 따라 달라진다 (압축기별 반복 항목이 있는 냉매계통만 가변, 나머지는 고정):

- **냉매계통**: `(토출압력 + 토출가스온도 + 흡입압력 + 오일압력) × N` + `냉매량(1) + 오일량(1)` = `4N + 2`행
- **냉수계통**: `냉각수온도(입/출 2) + 브라인온도(입/출 2)` = 고정 4행
- **전기계통**: `운전전압(1) + 운전전류(1) + 단자대&판넬상태(1)` = 고정 3행
- **기타**: `드레인상태(1) + 저압부단열재상태(1) + 이상진동및소음상태(1)` = 고정 3행

압축기 2대 장비 예시: 냉매계통 `4×2+2=10`행, 전체 `10+4+3+3=20`행 (+ 표 맨 아래 전체 폭 "비고" 안내문 1행, 병합 없이 별도).

## 11. 확인이 필요했던 부분 (결정 사항)

원문을 정리하면서 발견했던 의문점과 그에 대한 답변을 정리한다. 실제 내용 반영 위치는 각 항목에 링크로 표시했다.

- ✅ (정정 이력, 2단계) **운전일지의 냉각수온도/브라인온도/운전전압 분류** → 두 차례 바뀌었다. ① 최초엔 "api-manual.md의 채널 자동측정 7개 목록에 없다"는 이유로 브라인온도/운전전압을 양식에서 아예 뺐다가(잘못된 판단), 백엔드 소스로 이 둘이 실존하는 **사용자 직접입력** 항목임을 확인해 되살렸다. ② 이후(**2026-09-11**) 백엔드가 `Equipment`에 냉각수/브라인/전압 유무·min/max 속성을 추가하면서, 냉각수온도(원래 CH01 채널 자동측정)와 브라인온도·운전전압(원래 사용자 직접입력) **5개 전부**가 채널을 읽지 않는 **"장비설정 기반 랜덤값"**이라는 제3의 분류로 재편됐다. 현재 최신 상태는 [10장 자동화 동작](#10-운전일지)의 B그룹 참고.
- ⏳ **결재 완료 후 운전일지 수정을 막을지** → 백엔드 소스 주석으로 재확인됨: "사양 변경 가능성이 있어 백엔드에 강하게 고정하지 않기로 함" — **의도적으로 프론트 판단에 맡겨진 사항**. 1차 구현에서는 점검일지식 완전 잠금(`disabled`) 대신 **소프트 락**으로 우선 처리했다: 3단계 모두 결재 완료되면 안내 배너만 띄우고 입력은 계속 허용(`pages/operation/operation.js`). 실제 운영 요구사항과 맞는지는 아직 사용자 확인이 필요한 임시 기본값이다.
- ✅ **"기계 전류 ±10%"** → 오기 아니고 원문 그대로 사용. 다만 실측 기준값 자체가 사용자가 자유롭게 편집하는 항목이라 문구 정확성은 중요하지 않음.
- ✅ **비상정지 메뉴의 위치** → 별도 메뉴 없이, 실시간 현황에서 장비 행을 클릭해 들어가는 [장비 실시간 화면](#31-장비-실시간-화면)에 비상정지 카드를 두기로 함. 2026-09-29 실제 기능으로 연동 완료(3.1장 참고).
- ✅ **경보 이력 조회 메뉴의 위치** → 별도 메뉴 불필요. 실시간 현황/자료 조회의 이벤트 리스트로 충분하며, 어떤 이벤트를 남길지는 백엔드가 결정하고 프론트는 내려오는 이벤트를 그대로 표시만 한다. [3장 실시간 현황](#3-실시간-현황)에 반영.
- ✅ **첨부파일 형식/용량** → 파일당 최대 10MB, 모든 첨부파일은 필수가 아닌 선택 사항, 다중 파일 첨부 가능. [13장 첨부파일 공통 규칙](#13-첨부파일-공통-규칙) 참고.
- ⏳ **`/` 기호의 중의성** (점검·운전일지의 "통신오류" vs 결재란의 "해당없음") → **추후 결정 (보류)**. 현재는 원문 표기를 그대로 유지한다.

## 12. 결재 시스템 공통 규칙

점검일지를 비롯해 앞으로 추가될 문서(운전일지/교육훈련/수리보수일지 등)가 공통으로 쓰는 규칙이다. 문서마다 API 경로는 다르지만(예: 점검일지는 `/api/inspection-logs/{id}/approve`) 규칙 자체는 전부 동일하다 ([api-manual.md 10번](reference/api-manual.md) 기준).

### 결재 슬롯과 상태

- 결재 슬롯은 최대 3개, 항상 **안전관리원 → 안전관리책임자 → 안전관리총괄자** 순서로 고정이다. (`일반관리원`(2026-09-17 `일반관리자`에서 이름 변경)은 애초에 결재 슬롯 자체가 없다 — 조회만 가능.)
- 각 슬롯은 다음 4가지 상태 중 하나이며, 문서유형별로 어느 슬롯이 어떤 상태를 갖는지는 **시스템에 고정**되어 있다(사용자가 매번 선택하는 옵션이 아니다).
  | 상태 | 의미 | 화면 표시 |
  | --- | --- | --- |
  | 대기 | 아직 결재 안 됨, 승인 가능 | 승인 버튼 |
  | 승인 완료 | 결재자 이름·시각 있음 | 이름 + 일시 |
  | 해당없음 | 이 문서유형엔 이 결재단계가 원래 없음 | `/` |
  | 전결 | 이 문서유형은 이 단계를 항상 전결 처리하기로 고정 | `//전결` |
    - "해당없음"과 "전결"은 실제 승인 동작이 없다는 점에서 같고(결재자 이름·시각 없음), 화면 표시 문구만 다르다.
- **점검일지는 3단계 전부 실제로 결재를 받는다** (해당없음/전결 케이스 없음). 다른 문서유형은 다를 수 있다.

### 승인/취소 규칙

- 승인 API는 "누구를 승인시킬지"를 받지 않는다 — **호출한 사용자 자신의 역할 + 그 장비의 담당자 등록 여부**로만 어느 슬롯을 승인할지 자동 결정된다.
- **순서를 반드시 지켜야 한다** — 하위 단계가 끝나기(승인完료/해당없음/전결) 전에는 상위 단계를 승인할 수 없다.
- 반려 개념은 없다 — 승인 아니면 대기뿐이다.
- **결재가 하나라도 진행된 문서는 수정할 수 없다.** 다시 수정하려면 시스템관리자가 결재를 전체 리셋해야 한다. **단, 운전일지는 이 잠금 규칙 자체의 예외다** — 결재가 진행 중이어도 저장(`PUT`)이 항상 가능하다(점검일지와의 유일한 차이). 결재 완료 후 수정을 막을지는 프론트가 화면에서 직접 판단해서 처리해야 한다.
- 취소는 **자기 자신이 승인한 단계만**, 그리고 **상위 단계가 아직 승인되지 않았을 때만** 가능하다.

### 시스템관리자

- 시스템관리자는 결재를 직접 할 수 없다 (안전관리원/책임자/총괄자 역할이 아니므로).
- 대신 특정 문서의 결재를 **전부 무효화(리셋)**할 수 있다 — 진행 단계와 상관없이 전체 초기화해서 재결재를 요구하는 용도다.

### 프론트 구현상 알아둘 점

- 로그인 세션에는 로그인 아이디와 역할만 있고, 결재자 이름은 실명(성명)으로 내려오기 때문에 **"이 승인/취소가 로그인한 나 자신의 것인지"를 프론트가 미리 정확히 판단할 방법이 없다.** 담당 장비 등록 여부도 마찬가지로 사전 확인 API가 없다. 따라서 버튼은 "내 역할에 해당하는 슬롯"이면 일단 보여주고, 실제 클릭 시 서버가 돌려주는 오류로 안내하는 방식으로 처리한다.

## 13. 첨부파일 공통 규칙

공지사항, 검사 이력, 교육훈련 등 첨부파일을 다루는 모든 화면에 공통으로 적용된다. **수리보수 및 철거일지는 2026-09-16 사양 변경으로 첨부파일을 지원하지 않는다**(대상에서 제외).

- 파일당 최대 용량: **10MB 이하**
- 첨부파일은 **선택 사항**이며 필수 입력이 아니다.
- **다중 파일** 첨부가 가능하다.
